# Скилл `cards@1`: выделение → карточки

**Статус:** реализовано 26 октября 2026 (скилл `cards@1`). Ограничения — ниже.
**Дата:** 26 октября 2026.
**Связанные документы:** `spec/AI-agents-architecture.md`, `spec/AI-agents-v1.md`,
ADR-066 (агенты), ADR-106 (карточки и Kanban).

## 1. Задача

Человек выделяет стикеры, текст или фигуры и просит агента превратить их в карточки:
либо самостоятельные (рядом на доске), либо в конкретной колонке существующего
Kanban. Это второй скилл после `diagram` и первый, который меняет много объектов,
поэтому он же — полигон для change set.

## 2. Что уже есть в модели

- Карточка — виджет `type: "card"` с `title`, `content`, координатами и `parentId`
  (у карточки в Kanban `parentId` = id канбана).
- Размещение карточки в матрице хранится не в виджете, а в `board.kanbans`:
  `cards[cardId] = { columnId, swimlaneId, order }`.
- Добавление карточки — одна Yjs-транзакция: виджет + текст + запись размещения.
- **Чего нет:** исполнителя, срока, тегов, статуса как отдельного поля. Сейчас
  «статус» — это колонка, а `title`/`content` — единственный текст. Полноценные поля
  F15 — отдельное расширение модели и UI, а не этот скилл.

## 3. Манифест

```yaml
slug: cards
version: 1
name: Превратить выделение в карточки
required_capabilities: [board.read, board.edit]
tools: [read_selection, write_cards]
risk: write
handler: builtin:cards
input:
  source: selection | texts
  selectionIds: [string]          # до 100
  texts: [string]                 # альтернатива выделению, до 100
  target:
    kind: standalone | kanban
    kanbanId: string
    columnId: string
    swimlaneId: string
  mode: copy | move               # по умолчанию copy
  titleFrom: first_line | whole_text
output:
  created: [{ cardId, title, sourceId, columnId, swimlaneId }]
  skipped: [{ sourceId, reason }]
  count: integer
```

## 4. Поведение

1. **Источник.** Если `source=selection`, сервер читает тексты выбранных объектов из
   Yjs по id; клиентский текст не считается доверенным. Пустые и нетекстовые объекты
   попадают в `skipped`, а не создают пустые карточки.
2. **Заголовок.** `first_line`: первая непустая строка, обрезанная до 120 символов;
   остаток — в `content`. `whole_text`: весь текст в `title` (для коротких стикеров).
3. **Цель.**
   - `standalone`: карточки раскладываются сеткой в текущем виде (origin из задачи),
     без `parentId`.
   - `kanban`: карточки создаются с `parentId = kanbanId` и размещением в указанной
     колонке/дорожке, в порядке источников. Неизвестная колонка → ошибка до записи,
     а не «куда-нибудь».
4. **Режим.** `copy` оставляет источники; `move` удаляет их **в той же транзакции**
   после успешного создания. Удаление источников — отдельное явное действие, не
   побочный эффект копирования.
5. **Пределы.** До 500 карточек за задачу или change set; исполнение идёт чанками по
   50 с прогрессом. Больше — `CHANGE_SET_REQUIRED`. Текст одной карточки — до 10 000
   символов. При сбое позднего чанка задача завершается `CARDS_PARTIAL` с числом
   созданных карточек, а не притворяется успешной; change set можно продолжить
   (`resume`) с обработанных источников.
6. **Проверка.** Сначала валидируется весь пакет: права, существование канбана,
   колонки и дорожки, лимиты, бюджет. Любая ошибка валидации → ни одной записи.
7. **Идемпотентность.** Повтор того же `Idempotency-Key`/задачи не создаёт дубликатов;
   результат возвращает уже созданные карточки.
8. **Провенанс.** У карточек `createdBy`, `agent {id, taskId, skill}`, записи
   `agent_actions`, аудит `agent.write` с количеством.
9. **Бюджет.** `actions = cards`; при превышении `maxActions` — отказ до записи.
10. **Preview.** Для больших пакетов предусмотреть `dryRun`: вернуть план
    (сколько карточек, какие заголовки, куда) без изменения доски. В v1 допустим
    только для `<=100`.

## 5. Права

- Вызывающий должен иметь `board.edit`; агент — не сильнее владельца
  (`agentEffective()`), как и для диаграммы.
- `move` требует права удалять исходные объекты — это то же `board.edit`, но
  подтверждается отдельным флагом в задаче.
- Карточки в чужой Kanban не меняют его структуру: только добавление карточек в
  существующую колонку. Создание колонок/дорожек — отдельная операция, не этот скилл.
- Заблокированный объект-источник не удаляется в `move`; карточка создаётся, источник
  остаётся, в результате `skipped: locked_source`.

## 6. Приёмочные критерии

| ID | Given / When | Then |
|---|---|---|
| CARD-01 | Выделены 3 стикера, `copy` | Созданы 3 карточки с текстом; стикеры остались |
| CARD-02 | То же, `move` | Карточки созданы, стикеры удалены одной транзакцией |
| CARD-03 | Заголовок из первой строки | `title` — первая строка, остаток в `content` |
| CARD-04 | Kanban, колонка `Doing` | Карточки в `Doing`; порядок совпадает с порядком источников |
| CARD-05 | Неизвестная колонка | Ошибка до записи; доска не изменилась |
| CARD-06 | 501 источник | `CHANGE_SET_REQUIRED`; ни одной карточки |
| CARD-06b | 200 источников | Карточки создаются чанками; прогресс виден в задаче |
| CARD-07 | Повтор с тем же ключом | Дубликатов нет; тот же результат |
| CARD-08 | Бюджет `maxActions=2`, 3 источника | `BUDGET_ACTIONS`; ни одной карточки |
| CARD-09 | Источник заблокирован, `move` | Карточка создана, источник остался, причина в результате |
| CARD-10 | Пустые стикеры | Пропущены с причиной; пустые карточки не созданы |
| CARD-11 | Агент-владелец viewer | Доступ запрещён (`NO_CAPABILITY`), ничего не создано |
| CARD-12 | После выполнения | У карточек есть `agent`/`taskId`; в журнале `agent.write` |

## 7. Реализация (когда дойдём)

1. Доменная команда `convertToCards({ydoc, selectionIds, target, mode})` на сервере:
   чтение Yjs, валидация, одна транзакция на чанк, возврат id/ошибок (реализовано в
   `apps/sync/cards.mjs`).
2. Повторить инварианты `addCard`: виджет + `Y.Text` + запись в `board.kanbans` с
   `orderBetween`.
3. Скилл `cards` — тонкая обёртка: промпт не обязателен (источник — выделение), но
   модель может предложить заголовки/группировку; все поля валидируются.
4. Change set: `estimate` (dry run) → `preview` (draft) → `execute` → progress →
   `cancel`/`resume`; `Idempotency-Key` на создание. Реализовано для `create_cards`.
5. UI: в диалоге агента выбрать скилл, цель (standalone/kanban/колонка), режим
   copy/move; карточки идут через change set, прогресс виден в задаче.

## 8. Открытые вопросы

1. Нужны ли поля `assignee`, `due`, `tags` в карточке? Если да — сначала расширение
   модели/UI (F15), иначе скилл создаёт «карточку без полей».
2. `move` по умолчанию или `copy`? (Рекомендация: `copy`.)
3. Группировка по цвету/тегу в колонки — это `cards` или отдельный скилл `cluster`?
4. Нужен ли отдельный скилл «разложить существующие карточки по колонкам»?
5. Внешняя синхронизация карточек (Jira) — вне этого скилла.
