# ИИ-шлюз: изоляция и управление трафиком агентов

ТЗ к **ADR-251**. Статус: предложено, 2026-11-20. Связано с ADR-109, исходящим клиентом `apps/sync/outbound.mjs` и
`spec/AI-agents-v1.md`.

## 0. Цель и границы

**Цель — изоляция и управление**, а не обход ограничений провайдеров. Все вызовы моделей
агентами remo идут через отдельный сервис `remo-ai-gateway` на отдельном VPS. Только он
выходит к провайдерам моделей.

Что даёт шлюз:
1. **Изоляция.** Отдельная машина, отдельный исходящий IP, отдельная сеть. Медленные и
   зависшие провайдеры и всплески задач не трогают сервер с комнатами.
2. **Понятный список провайдеров.** Только перечисленные в реестре адреса, модели и
   правила. Всё остальное отклоняется.
3. **Управление на ходу.** Выключатели (всё, провайдер, организация, пользователь), лимиты
   частоты и токенов, перезагрузка конфигурации без перезапуска remo.
4. **Наблюдаемость.** Метрики и журнал метаданных: кто, куда, сколько, с каким результатом.
   Без текстов запросов и ключей.

**Вне объёма v1:** потоковые ответы (`ai.mjs` их не использует), кеш ответов, автоматический
выбор «самой дешёвой» модели, перенос выполнения агентов из sync, отдельный сервер для
входящих внешних агентов (для них — отдельный адрес и лимиты, §8).

## 1. Почему свой шлюз, а не LiteLLM

| | Свой шлюз | LiteLLM Proxy |
|---|---|---|
| Что нужно remo | один маршрут `POST /v1/chat/completions` без потоков | сотни провайдеров и функций |
| Стек | Node 22, без зависимостей, тот же, что remo | Python, PostgreSQL для ключей и бюджетов, Redis |
| Цепочка поставки | наш код в нашем репозитории | в 2026 году два взлома публикации пакетов (март и октябрь) и несколько CVE с обходом авторизации |
| Нужные нам функции | все в объёме v1 | журнал аудита, ограничение маршрутов, своя авторизация с виртуальными ключами — платные (Enterprise) |
| Объём | ~600–900 строк с тестами | отдельная платформа со своей админкой |

Шлюз — точка, через которую проходят все ключи моделей. Такую точку лучше держать
маленькой и полностью своей. Если позже понадобятся сотни провайдеров или сложная
маршрутизация, решение пересматривается отдельным ADR.

## 2. Устройство

```
 VPS 1: remo                                VPS 2: ai-gateway
┌──────────────────────────────┐ WireGuard ┌──────────────────────────────────┐
│ sync                         │ 10.77.0.0/30                                 │
│  agent-call.mjs              │           │ :8080 только на wg0               │
│  AiClient ── POST ───────────┼──────────►│  auth (токен) → реестр →          │──► HTTPS к
│   /v1/chat/completions       │           │  выключатели → лимиты →           │    провайдерам
│   + X-Remo-* заголовки       │◄──────────┼── ответ ◄── outbound (DNS-pin) ◄──│    из реестра
│  ai_runs (журнал как сейчас) │           │ журнал метаданных, /metrics       │
└──────────────────────────────┘           │ admin API :8081 только 127.0.0.1  │
                                           └──────────────────────────────────┘
```

- **Код шлюза — в монорепозитории:** `apps/ai-gateway` (AGPL). Self-host может поставить
  его тоже, но не обязан: без шлюза remo ходит к провайдерам напрямую, как сейчас.
- **Общий код с sync.** Исходящий клиент (`apps/sync/outbound.mjs`) переезжает в
  `packages/outbound`, и им пользуются sync и шлюз (правило 1 `AGENTS.md`: один механизм).
  Его гарантии сохраняются: DNS-пиннинг, запрет приватных адресов, запрет перенаправлений.
- **Транспорт до шлюза** — HTTPS с самоподписанным сертификатом, закреплённым в sync
  (`REMO_AI_GATEWAY_CA`), а не `http://`: исходящий клиент не ослабляется, приватный адрес
  разрешается точечно для этого вызова. Второго транспорта нет.

## 3. Контракт sync → шлюз

### 3.1 Запрос

`POST {REMO_AI_GATEWAY_URL}/v1/chat/completions` — тело OpenAI-совместимое, ровно то, что
`AiClient` отправляет сейчас (`model`, `messages`, `max_tokens`, `temperature`,
`response_format`, `usage`).

| Заголовок | Значение |
|---|---|
| `Authorization` | `Bearer <REMO_AI_GATEWAY_TOKEN>` — общий секрет sync и шлюза |
| `X-Remo-Upstream` | id провайдера из реестра (`openrouter`, `openai`, `yandex`…) **или** базовый URL ключа пользователя (BYOK) |
| `X-Remo-Upstream-Key` | ключ провайдера: ключ пользователя (BYOK) или ключ установки |
| `X-Remo-Org`, `X-Remo-User` | id организации и владельца агента |
| `X-Remo-Task` | id задачи агента (для журнала и идемпотентности) |
| `X-Remo-Region` | `ru` / `eu` — регион установки из `REMO_AI_REGION` (§3.3), для правил реестра |
| `X-Request-Id` | id запроса для сквозного поиска в логах |

Ключ провайдера передаётся в заголовке внутри туннеля. Шлюз его не хранит и не пишет в лог
(§7). Ключи установки (не BYOK) можно хранить в шлюзе (§4.1, `keyEnv`), тогда sync их не
передаёт.

### 3.2 Ответ

- Успех — ответ провайдера как есть (статус 200 и JSON) плюс заголовки:
  - `X-Remo-Gateway-Provider: <id>`;
  - `X-Remo-Gateway-Latency-Ms`;
  - `X-Remo-Gateway-Usage: in=…,out=…`.
- Ошибка шлюза — JSON `{ "error": { "code": "...", "message": "..." } }` с кодами:

| HTTP | `code` | Когда | Что видит пользователь в remo |
|---|---|---|---|
| 401 | `GATEWAY_AUTH` | неверный токен sync | ошибка конфигурации, алерт оператору |
| 403 | `PROVIDER_NOT_ALLOWED` | upstream не в реестре или модель не разрешена | «Этот провайдер или модель не разрешены на сервере» |
| 403 | `REGION_NOT_ALLOWED` | провайдер запрещён для региона | то же |
| 423 | `KILLED` | сработал выключатель (с `scope`: `global`, `provider`, `org`, `user`) | «ИИ временно недоступен» + текст оператора, если задан |
| 429 | `RATE_LIMITED` | превышен лимит частоты или токенов (`Retry-After`) | «Слишком много запросов к ИИ, попробуйте через N минут» |
| 502 | `UPSTREAM_ERROR` | провайдер ответил ошибкой; его статус в `upstreamStatus` | как сейчас для ошибок провайдера |
| 504 | `UPSTREAM_TIMEOUT` | провайдер не ответил за `timeoutMs` | «Модель не ответила вовремя» |
| 503 | `GATEWAY_BUSY` | превышен предел одновременных запросов | «ИИ перегружен, попробуйте позже» |

### 3.3 Изменения в sync

- **`AiClient`** (`apps/sync/ai.mjs`):
  - при заданном `REMO_AI_GATEWAY_URL` все вызовы идут на шлюз с заголовками §3.1;
  - адрес шлюза — единственный приватный адрес, который разрешён исходящему клиенту, и
    только для этого вызова. Флаг `allowPrivate` пользовательских ключей не включает;
  - коды §3.2 превращаются в `AiError` с теми же кодами и понятными текстами (i18n в
    клиенте);
  - повтор без `response_format` при 400 сохраняется, но только для `UPSTREAM_ERROR` с
    `upstreamStatus = 400`.
  - `configured` больше не требует ключа: в режиме шлюза достаточно `REMO_AI_GATEWAY_URL` и
    токена, ключ может жить в шлюзе (`keyEnv`). Признак «настроено» — отдельный геттер, старые
    тесты не меняют поведения без переменной.
- **Режим шлюза fail-closed.** Если шлюз задан, но недоступен, — ошибка
  `AI_GATEWAY_UNAVAILABLE`. Прямого обхода нет, иначе изоляция незаметно пропадёт.
- **`agent-call.mjs`.**
  - Для BYOK в `X-Remo-Upstream` идёт базовый URL ключа. Шлюз сам сопоставит его с реестром.
  - При сохранении ключа пользователя (`agent-api-ai.mjs`) в режиме шлюза sync спрашивает
    `GET /v1/upstreams/check?baseUrl=` (тот же токен). Если провайдер не в реестре, ключ не
    сохраняется: `422 PROVIDER_NOT_ALLOWED` с текстом «Этот провайдер не подключён на
    сервере».
- **`packages/outbound`** создаётся переносом `apps/sync/outbound.mjs`; `isPrivateHost`
  выносится из `secrets.mjs` в пакет, иначе шлюз тянет весь модуль KEK. Четыре импортёра
  (`ai.mjs`, `agent-api-ai.mjs`, `sync-events.mjs`, `webhooks.mjs`) переключаются на
  `@remo/outbound`, поведение не меняется.
- **`probeProvider`** при сохранении BYOK в режиме шлюза ходит в `GET /v1/upstreams/check`, а
  не напрямую к провайдеру: прямая проверка обошла бы изоляцию.
- **Журнал `ai_runs`.** Без изменений по смыслу, плюс поле `gateway_provider` из заголовка
  ответа. `ai_runs.gateway_provider` — схема 26 (`alter table ai_runs add column if not exists
  gateway_provider text`). Поле входит в каноническую форму хеша; уже записанные строки
  пересчитываются чтением (`null` = прямой вызов), цепочка не переписывается.
- **Бюджет задачи** (токены и секунды) остаётся в sync. Шлюз отвечает за лимиты по времени
  и по организациям, sync — за бюджет одной задачи.

Новые переменные sync:

| Переменная | Значение |
|---|---|
| `REMO_AI_GATEWAY_URL` | `https://10.77.0.2:8080` |
| `REMO_AI_GATEWAY_TOKEN` | общий секрет, 32 байта |
| `REMO_AI_GATEWAY_CA` | CA самоподписанного сертификата шлюза (PEM) |
| `REMO_AI_GATEWAY_TIMEOUT_MS` | таймаут до шлюза; по умолчанию `REMO_AI_TIMEOUT_MS + 5000` |
| `REMO_AI_REGION` | `ru` или `eu` — регион установки для `X-Remo-Region`; не задан — заголовок не отправляется, правила `regions` — по конфигу шлюза |

Без `REMO_AI_GATEWAY_URL` поведение remo не меняется.

## 4. Реестр провайдеров и настройка

### 4.1 Файл конфигурации

`/etc/remo-ai-gateway/config.json` (права 600). Перечитывается по `SIGHUP` и командой
`reload`; при ошибке валидации остаётся прежняя конфигурация, а в лог пишется ошибка.

```json
{
  "region": "eu",
  "listen": "10.77.0.2:8080",
  "admin": "127.0.0.1:8081",
  "limits": {
    "concurrency": 32,
    "perOrg":  { "rpm": 30,  "tokensPerDay": 2000000 },
    "perUser": { "rpm": 15,  "tokensPerDay": 500000 },
    "global":  { "rpm": 600 }
  },
  "providers": [
    {
      "id": "openrouter",
      "baseUrl": "https://openrouter.ai/api/v1",
      "match": ["https://openrouter.ai/api/v1"],
      "models": ["*"],
      "regions": ["eu"],
      "timeoutMs": 60000,
      "rpm": 300,
      "byok": true,
      "keyEnv": "OPENROUTER_KEY",
      "price": { "inPerMTok": 0, "outPerMTok": 0 },
      "enabled": true
    },
    {
      "id": "yandex",
      "baseUrl": "https://llm.api.cloud.yandex.net/v1",
      "match": ["https://llm.api.cloud.yandex.net/v1"],
      "models": ["yandexgpt*"],
      "regions": ["ru"],
      "byok": true,
      "enabled": true
    }
  ]
}
```

| Поле | Смысл |
|---|---|
| `id` | имя провайдера, используется в `X-Remo-Upstream` и в командах |
| `baseUrl` | куда шлюз шлёт запрос; только `https://` |
| `match` | какие базовые URL ключей пользователей (BYOK) считаются этим провайдером; точное совпадение после нормализации (без `/` в конце, нижний регистр хоста) |
| `models` | разрешённые модели: точные имена или шаблон с `*` в конце |
| `regions` | в каких регионах установки провайдер разрешён |
| `timeoutMs`, `rpm` | таймаут и предел частоты именно для провайдера |
| `byok` | можно ли пользоваться ключами пользователей |
| `keyEnv` | имя переменной окружения шлюза с ключом установки (если есть) |
| `price` | для подсчёта стоимости в метриках; не влияет на доступ |
| `enabled` | выключенный провайдер отвечает `KILLED` со `scope: provider` |

Чего нет в реестре, того нет. Произвольный базовый URL от пользователя без записи в
реестре отклоняется (`PROVIDER_NOT_ALLOWED`).

`/v1/upstreams/check` отвечает `{ allowed: boolean, provider?: string }`; неизвестный
`baseUrl` — `403 PROVIDER_NOT_ALLOWED`.

### 4.2 Состояние выключателей

Выключатели и временные изменения лимитов меняются часто и не должны требовать правки
конфигурации. Они живут в `/var/lib/remo-ai-gateway/state.json` (атомарная запись через
временный файл):

```json
{
  "kill": {
    "global":   { "on": false },
    "provider": { "openrouter": { "on": true, "reason": "инцидент у провайдера", "until": "2026-11-21T10:00:00Z" } },
    "org":      { "3f2c…": { "on": true, "reason": "злоупотребление" } },
    "user":     {}
  },
  "limitOverrides": { "org": { "9a1b…": { "tokensPerDay": 5000000 } } },
  "usage": { "day": "2026-11-20", "org": { "3f2c…": 812345 }, "user": { } }
}
```

- `until` снимает выключатель автоматически.
- Счётчики суточных токенов сохраняются раз в минуту и при остановке. После перезапуска
  шлюз продолжает с сохранённых значений.

### 4.3 Управление: CLI

Команда `remo-gw` работает на машине шлюза и вызывает admin API на `127.0.0.1:8081` с
токеном из `/etc/remo-ai-gateway/admin.token`.

```
remo-gw status                         # версия, конфиг, выключатели, нагрузка
remo-gw providers                      # таблица: id, enabled, регионы, модели, rpm, ошибки/час, p95
remo-gw providers test <id> [--model m]  # пробный запрос с ключом установки
remo-gw kill global|provider <id>|org <id>|user <id> [--reason "..."] [--for 2h]
remo-gw unkill global|provider <id>|org <id>|user <id>
remo-gw limits                         # действующие лимиты и переопределения
remo-gw limits set org <id> --tokens-per-day 5000000 [--rpm 60]
remo-gw usage [--org <id>] [--day 2026-11-20]   # токены и стоимость
remo-gw reload                         # перечитать config.json
remo-gw tail [--org <id>] [--status error]      # живой журнал метаданных
```

- Каждое действие пишет строку в журнал администрирования (`admin.log`: кто, что, когда,
  причина).
- Добавление и удаление провайдера — правка `config.json` и `reload`. Конфиг можно держать в
  отдельном приватном репозитории с историей изменений.

Веб-панель — вне объёма v1. При необходимости позже её подключат к тому же admin API.

## 5. Обработка запроса в шлюзе

1. **Авторизация.** `Authorization` сравнивается с токеном постоянным временем. Неверный —
   `401` и метрика.
2. **Разбор.** Размер тела не больше 2 МиБ. Тело — JSON с `model` и `messages`.
3. **Провайдер.** По `X-Remo-Upstream` (id или `match`), затем модель по `models`, регион по
   `regions`, BYOK по `byok`. Если нет ключа ни в заголовке, ни в `keyEnv`, — `403`.
4. **Выключатели** в порядке `global` → `provider` → `org` → `user`.
5. **Лимиты.**
   - Частота: скользящее окно на минуту по `global`, провайдеру, организации и пользователю.
   - Суточные токены по организации и пользователю: учитываются после ответа по `usage`, а
     до запроса проверяется, что лимит ещё не исчерпан.
   - Одновременные запросы: семафор `concurrency`; ожидание до 2 с, затем `503`.
6. **Вызов** через `packages/outbound`: DNS-пиннинг, запрет приватных адресов, запрет
   перенаправлений, таймаут провайдера. Заголовки к провайдеру — только `Authorization`,
   `Content-Type`, `X-Title`. Заголовки `X-Remo-*` наружу не уходят.
7. **Ответ** sync как есть (§3.2), учёт токенов и стоимости, запись в журнал §7.

## 6. Сеть и развёртывание

### 6.1 WireGuard

- Отдельная подсеть `10.77.0.0/30`: VPS 1 = `10.77.0.1`, VPS 2 = `10.77.0.2`.
- В `AllowedIPs` у каждой стороны — только адрес другой стороны. Порт WireGuard на VPS 2
  открыт только для IP VPS 1.
- Пример конфигурации и шаги — `deploy/ai-gateway/wireguard.md` (ключи генерируются на
  месте, в репозиторий не попадают).

### 6.2 Межсетевой экран VPS 2 (nftables, пример в `deploy/ai-gateway/nftables.conf`)

- **Входящие:** SSH (по ключу, с белого списка IP), UDP-порт WireGuard от VPS 1; на `wg0` —
  только TCP 8080 от `10.77.0.1`. Всё остальное запрещено.
- **Исходящие:** TCP 443 и DNS. Остальное запрещено (шлюзу больше ничего не нужно).
- Admin API слушает только `127.0.0.1`.

### 6.3 Запуск

- `deploy/ai-gateway/compose.yml`: один контейнер `remo-ai-gateway`, `read_only: true`,
  `no-new-privileges`, том для `state.json` и логов, `network_mode: host`, чтобы слушать
  `wg0`. Либо unit systemd `deploy/ai-gateway/remo-ai-gateway.service` — оба варианта
  описать, выбрать один в `guide/admin/deploy`.
- Переменные шлюза:
  - `GATEWAY_TOKEN`, `GATEWAY_ADMIN_TOKEN_FILE`, `GATEWAY_CONFIG`, `GATEWAY_STATE_DIR`;
  - `keyEnv`-ключи провайдеров.
- Здоровье:
  - `GET /healthz` на `wg0` — без токена, без подробностей;
  - `GET /metrics` на `wg0` — с токеном метрик.

### 6.4 VPS для шлюза

1 vCPU, 1 ГБ ОЗУ достаточно: шлюз почти всё время ждёт ответов провайдеров. Регион VPS —
по правилам установки, см. оговорку §9.

## 7. Наблюдаемость

**Метрики Prometheus** (`/metrics`; без id организаций в метках — их слишком много):
- `remo_gw_requests_total{provider,model,status}`;
- `remo_gw_latency_seconds{provider}` — гистограмма;
- `remo_gw_tokens_total{provider,direction}`;
- `remo_gw_cost_total{provider}`;
- `remo_gw_killed_total{scope}`;
- `remo_gw_rate_limited_total{scope}`;
- `remo_gw_inflight`;
- `remo_gw_upstream_errors_total{provider,code}`.

**Журнал метаданных** — JSON-строки в `/var/lib/remo-ai-gateway/requests.log`, ротация по
суткам, хранение 30 дней:

```json
{"ts":"…","rid":"…","org":"…","user":"…","task":"…","provider":"openrouter",
 "model":"…","status":200,"code":null,"latencyMs":1830,"in":1520,"out":410,"cost":0.0012}
```

**Никогда не пишется:** тело запроса и ответа, ключи, заголовок `Authorization`, текст
ошибки провайдера целиком (только код и первые 200 символов с вырезанными
`sk-…`/`Bearer …`).

**Сводка по организациям:** `remo-gw usage` строится по журналу и счётчикам. Для отчётов
владельцу этого достаточно.

**Алерты** через существующий мониторинг:
- доля ошибок провайдера > 20% за 10 минут;
- шлюз недоступен из sync (метрика sync `remo_ai_gateway_unavailable_total`);
- суточный общий расход выше порога из конфига (`limits.global.costPerDay`).

## 8. Входящие внешние агенты: отдельный адрес и лимиты

Внешние агенты и интеграции (MCP-сервер, токены `remo_it_…`, маршруты `/agent/...`) остаются
в sync, но получают **отдельный адрес** `agents.<домен>`:

- **Отдельный `server` в nginx** (`deploy/nginx-remo-agents.conf`).
  - Проксирует только API-маршруты агентов и интеграций. Статики приложения и сокетов там
    нет.
  - Свои зоны `limit_req` и `limit_conn`: по токену (`$http_authorization` хешем) и по IP.
  - `client_max_body_size` как у API.
- **На основном адресе** API с bearer-токенами продолжает работать для совместимости. В
  документации рекомендуется `agents.<домен>`. Через одну минорную версию основной адрес
  начинает отвечать на такие запросы заголовком `Deprecation`.
- **Метрики sync по источнику:** запросы с bearer-токеном получают метку `source=agent` в
  существующих метриках HTTP. Так нагрузка агентов видна отдельно от людей.

Перенос `agents.<домен>` на отдельный экземпляр — когда метрики покажут необходимость,
отдельным решением.

## 9. Оговорки

- **Шлюз не меняет юридическую сторону передачи данных.** Если тексты российских
  пользователей уходят к зарубежному провайдеру модели, это трансграничная передача по
  152-ФЗ независимо от того, где стоит шлюз. Для российской установки реестр должен
  содержать провайдеров, которые это допускают, и политика конфиденциальности должна это
  описывать.
- **Условия провайдеров.** Шлюз не используется для доступа к провайдерам из регионов,
  которые те не обслуживают. Поле `regions` в реестре помогает это соблюдать.

## 10. Тесты

**Шлюз (`apps/ai-gateway`, vitest):**
- авторизация: неверный и пустой токен, сравнение постоянным временем;
- реестр: upstream по id и по `match`, нормализация URL, модель по шаблону, регион, `byok:
  false`, неизвестный провайдер → `403`;
- выключатели: каждый `scope`, порядок проверки, `until` снимает сам;
- лимиты:
  - частота по каждому уровню;
  - суточные токены с переходом через полночь UTC;
  - сохранение и восстановление `state.json`;
  - семафор `concurrency` и `503`;
- вызов провайдера (поддельный HTTP-сервер):
  - 200, 400, 429, 500;
  - таймаут;
  - перенаправление отклоняется;
  - приватный адрес в DNS отклоняется;
  - заголовки `X-Remo-*` не уходят наружу;
- журнал: в строках нет ключей и тел (поиск по заранее подложенному маркеру в запросе);
- `reload` с битым конфигом оставляет прежний.

**sync:**
- `AiClient` в режиме шлюза: заголовки §3.1, перевод кодов §3.2 в `AiError`;
- fail-closed: при недоступном шлюзе прямых вызовов нет;
- сохранение BYOK-ключа неразрешённого провайдера → `422`;
- без `REMO_AI_GATEWAY_URL` все существующие тесты агентов проходят без изменений.

**Сквозной (`docker-compose.test.yml`):** sync + шлюз + поддельный провайдер.
- Задача агента проходит через шлюз.
- `remo-gw kill org` даёт в интерфейсе «ИИ временно недоступен».
- `unkill` возвращает работу.

## 11. Этапы

1. **Общий код.** `packages/outbound` (перенос без изменения поведения, все тесты зелёные).
2. **Шлюз.** `apps/ai-gateway`: контракт §3, реестр §4.1, обработка §5, состояние §4.2,
   метрики и журнал §7, CLI §4.3, тесты.
3. **sync.** Режим шлюза в `AiClient`, проверка BYOK, fail-closed, `gateway_provider` в
   `ai_runs`, тексты ошибок RU/EN.
4. **Развёртывание.** WireGuard, nftables, compose и systemd, документация
   (`guide/admin/deploy`, `guide/reference/env`), алерты.
5. **Внешние агенты.** `agents.<домен>` в nginx, метка `source=agent`, документация.

## 12. Приёмка

1. `pnpm verify --e2e` зелёный с режимом шлюза и без него.
2. На паре VPS с WireGuard задача агента выполняется через шлюз. С VPS 1 напрямую к
   провайдеру не уходит ни одного соединения (проверка `ss`/`conntrack` во время прогона).
3. Порт шлюза недоступен из интернета (внешний скан), admin API недоступен даже из туннеля.
4. `remo-gw kill provider openrouter` за 1 с переводит новые задачи в «ИИ временно
   недоступен», `unkill` возвращает. remo не перезапускался.
5. Добавление провайдера правкой `config.json` и `reload` делает его доступным для BYOK без
   релиза remo.
6. В журнале шлюза за прогон нет ни ключей, ни фрагментов текстов запросов.
7. Отказ шлюза (остановка контейнера) не роняет sync. Комнаты работают, агенты отвечают
   понятной ошибкой.
