# AI-агенты: архитектура и требования к безопасности

**Статус:** ключи и доказательный журнал, скилл `cards`, change sets
(`create_cards`, `create_connector`, `set_connector_waypoints`,
`set_connector_routing`) и MCP v0 реализованы 26–27 октября 2026. Новые операции change set,
remote MCP с OAuth и внешний SDK — следующие этапы.
**Дата:** 26 октября 2026.
**Связанные документы:** `spec/AI-agents-v1.md` (v1), ADR-066 (агенты), ADR-061 (`effective()`),
`spec/IAM-v1.md`.

## 0. Что уже реализовано

| Часть | Состояние |
|---|---|
| Ключи на пользователя и организацию в `ai_credentials` | **есть**: scope, provider, model, default, ротация, отзыв |
| Envelope encryption | **есть**: AES-256-GCM, DEK на ключ, KEK из `REMO_KEK`; KMS — следующий шаг |
| Write-only API | **есть**: секрет не возвращается, fingerprint, `test`, политика `either/org/personal` |
| Доказательный журнал | **есть**: `ai_runs`, хэш-цепочка по организации, `verify`, UI |
| Внешний якорь | **есть**: файл или endpoint (`REMO_AI_ANCHOR_*`), ежедневно и при старте |
| Скилл `cards` | **есть**: copy/move, standalone/kanban, до 500, чанки по 50, прогресс, `Idempotency-Key` |
| Change set / jobs | **есть**: операции, dry-run estimate, preview, execute, progress, cancel, resume, idempotency; исполнитель — задача |
| MCP | **есть v0**: stdio-фасад над rooms/skills/change sets; OAuth и remote transport — нет |
| Внешний SDK | **нет** |

Текущая реализация ключей и журнала описана в ADR-067; ограничения — в конце раздела 3
и 4 (KEK, якорь, компрометация процесса).

## 1. Короткий ответ на вопрос «MCP или скиллы»

**Ни то, ни другое в одиночку. Скиллы — это доменный слой и граница безопасности;
MCP — тонкий транспортный фасад над ним; массовая работа идёт через change sets и
jobs.**

- **Скилл** — версионированная доменная операция с манифестом: какие capabilities
  нужны, какие инструменты доступны, какой риск, какой результат. Сервер проверяет
  манифест против задачи и роли владельца. Это то, что нельзя делегировать протоколу.
- **MCP** — стандартный способ показать эти операции внешнему агенту (Claude, IDE,
  другому клиенту). Он не является моделью прав, не даёт атомарности и не решает
  массовые операции. Если сделать MCP единственным интерфейсом, агент будет делать
  тысячи мелких вызовов, а безопасность придётся изобретать в каждом инструменте.
- **Change set** — пакет связанных изменений с временными ссылками, валидацией,
  оценкой, preview, идемпотентностью, возобновлением и аудитом. Это ответ на «1000
  стикеров в 20 группах», а не «вызови create_sticky 1000 раз».
- **Job** — асинхронное исполнение принятого change set с прогрессом, отменой и
  бюджетом. Очередь не заменяет лимиты, а делает перегрузку управляемой.

Направление «MCP + типизированный SDK + change sets + jobs» опирается на **один доменный
слой команд для UI, API, MCP и SDK**. Разные реализации прав в четырёх местах — это
способ получить четыре разные дыры.

### Что это значит для нас

| Этап | Что делаем | Почему |
|---|---|---|
| Сейчас | Скиллы (`diagram`, затем `cards`) вызывают доменные команды напрямую | Уже есть `agentEffective()` и Yjs; не нужен новый протокол |
| Следом | Change set для массовых операций (карточки, кластеры, импорт) | Один вызов модели и один пакет вместо тысяч |
| Потом | MCP-фасад для внешних агентов | Только когда есть внешние клиенты и стабильный доменный слой |
| Позже | SDK/CLI и jobs для длительных задач | Для программируемых агентов и больших пакетов |

**Для скилла «карточки» MCP не нужен.** Это доменная операция: взять выделение,
создать карточки, разложить по колонкам. Ей нужны валидация, бюджет, провенанс и
пакетность, а не новый протокол.

## 2. Слои, которые нельзя смешивать

```text
UI (React)        HTTP API        MCP (future)        SDK/CLI (future)
     \               |                /                    /
      \              |               /                    /
       └───────── доменный слой команд ──────────────────┘
                 (create/update/delete, change set,
                  validate, estimate, permissions)
                              │
                    agentEffective() + effective()
                              │
                 исполнители (Yjs-комнаты, очереди)
                              │
                 состояние + события + аудит
```

Правила:

1. **UI, HTTP, MCP и скилл вызывают одни и те же команды.** Никакого «MCP-специального»
   пути, который умеет больше.
2. **Права проверяются в доменном слое**, не в инструменте MCP и не в промпте.
3. **Инструмент MCP не получает произвольный доступ к БД или сети.** Он вызывает
   доменную команду с задачей и capability.
4. **Большая работа возвращает handle**, а не поток объектов: `change_set_id`,
   `job_id`, `progress`, `next_poll_ms`.
5. **Ошибки политики не повторяются автоматически** как временные.

## 3. Ключи провайдеров: у пользователя и у организации

Цель: у человека и у организации может быть **свой** ключ и модель; мы за них не
платим; ключ нельзя прочитать через API, админку, логи или дамп базы.

### 3.1. Модель данных

```sql
ai_credentials(
  id uuid pk,
  scope text check (scope in ('user','org')),
  scope_id uuid not null,              -- users.id или orgs.id
  provider text not null,              -- openrouter | cerebras | openai | custom
  label text not null default '',
  base_url text not null,              -- только https, allowlist
  model text,                          -- модель по умолчанию
  ciphertext bytea not null,           -- AES-256-GCM(secret)
  nonce bytea not null,
  dek_wrapped bytea not null,          -- DEK, зашифрованный KEK
  dek_nonce bytea not null,
  kek_id text not null,                -- какая версия KEK
  fingerprint text not null,           -- sha256(secret), первые 16 hex; не секрет
  is_default boolean not null default false,
  state text check (state in ('active','revoked')),
  created_by uuid, created_at, rotated_at, last_used_at
)
```

- `scope=user` — личный ключ; `scope=org` — ключ организации.
- Один default на `(scope, scope_id, provider)` — частичный уникальный индекс.
- Сам секрет **никогда** не хранится открытым и **никогда** не возвращается API.
  Наружу — только метаданные и `fingerprint` (например, `…a1b2c3d4`).
- `base_url` — это тоже потенциальная утечка: пользовательский URL может увести
  содержимое комнаты. **Именованный провайдер закреплён за своим endpoint**; другой URL
  возможен только как `provider: "custom"`. Для custom хост проверяется при сохранении
  и при каждом запросе.
- **Один outbound-клиент** (`outbound.mjs`, ADR-109). Только HTTPS; резолвятся все
  адреса; приватные, loopback, link-local, unique-local, multicast и IPv4-mapped IPv6
  отклоняются; соединение привязывается к проверенному IP через `lookup` сокета; TLS
  получает имя хоста для SNI; редиректы запрещены; тело ответа ограничено; произвольные
  заголовки не передаются. Прямой `fetch` к провайдеру в коде не используется.

### 3.2. Шифрование

- **Envelope encryption.** Для каждого секрета — случайный 32-байтный DEK;
  AES-256-GCM; AAD связывает `credential_id + scope + scope_id + provider`.
- DEK заворачивается **KEK**, который не лежит в базе: переменная окружения
  (32 байта, base64) в v1, KMS/HSM — цель следующей итерации. Смена KEK
  переворачивает только обёртки DEK, не перешифровывая все секреты.
- Расшифровка — в одном узком месте, непосредственно перед вызовом провайдера;
  буфер затирается после использования (best effort в JS). Кэша секретов нет.
- Секреты не попадают в логи, трассировки, error messages, audit и HAR. Отдельный
  тест на редактирование логов обязателен.
- Администратор организации видит метаданные ключа организации, но не секрет.
  Личные ключи не видит даже `org_admin` (иначе это обход доверия пользователя).

**Честная граница:** шифрование защищает дамп базы, бэкап и кражу диска. Если
скомпрометирован процесс, который вызывает провайдера, он может использовать ключ,
пока ключ не отозван. Поэтому: KMS/HSM, короткое время жизни расшифровки, egress
allowlist, лимиты, аномалии и быстрый отзыв — часть дизайна, а не «потом».

### 3.3. Выбор ключа

Порядок разрешения для задачи:

1. `task.credential_id` (явный выбор на один запуск);
2. `agent.credential_id` (ключ, закреплённый за агентом);
3. личный default владельца;
4. default организации;
5. `REMO_AI_API_KEY` — только как bootstrap для инсталляции/разработки.

Политика организации `ai_key_mode`:

- `either` (по умолчанию): личный или организационный;
- `org`: только ключ организации (данные не уходят через личные ключи);
- `personal`: только личные (организация не платит и не хранит ключ).

Если ключа нет — `AI_NOT_CONFIGURED`, задача не создаётся или падает до вызова.
Модель выбирается так же: задача → агент → ключ → политика; организация может
ограничить список моделей.

### 3.4. API (черновик)

```
GET    /users/me/ai/credentials              метаданные своих ключей
POST   /users/me/ai/credentials              {provider, baseUrl?, model?, label, secret}
DELETE /users/me/ai/credentials/{id}
POST   /users/me/ai/credentials/{id}/rotate  {secret}
POST   /users/me/ai/credentials/{id}/test    проверить ключ, ничего не сохранять

GET    /orgs/{org}/ai/credentials            org_admin: метаданные
POST   /orgs/{org}/ai/credentials
DELETE /orgs/{org}/ai/credentials/{id}
POST   /orgs/{org}/ai/credentials/{id}/rotate
POST   /orgs/{org}/ai/credentials/{id}/test
GET/PUT /orgs/{org}/ai/policy                {keyMode, providers, models}
```

Все ответы — write-only для секрета: `secret` принимается, но не возвращается.
`/test` делает минимальный запрос к провайдеру с лимитом и не пишет prompt.

### 3.5. Угрозы и контроли

| Угроза | Контроль |
|---|---|
| Дамп базы/бэкап | ciphertext + wrapped DEK; без KEK бесполезно |
| Кража KEK | версионирование KEK, ротация, переупаковка DEK, отзыв ключей провайдера |
| Чтение админом/саппортом | API не отдаёт секрет; UI только metadata/fingerprint |
| Логи/трейсы | запрет тел запросов, редактирование Authorization, тест на утечку |
| Скомпрометированный процесс | KMS, короткая расшифровка, egress allowlist, лимиты, аномалии, отзыв |
| Подмена base_url | allowlist, HTTPS, запрет редиректов и внутренних адресов |
| Слабый ключ/перебор | не относится к ключу провайдера; лимит на создание/тест |
| Утечка ключа у пользователя | fingerprint + audit, отзыв/ротация, задачи падают с `AI_CREDENTIAL_REVOKED` |
| Ключ в frontend | секрет вводится в форму, уходит на сервер, дальше живёт только на сервере |

## 4. Доказательный журнал сессий агента

Требование: «все сессии AI-агентов и их ключевые параметры логируются доказательно».
Значит, нужен журнал, к которому нельзя незаметно дописать/переписать запись.

### 4.1. Что считается сессией

- **Сессия** = `agent_task` от создания до терминального статуса.
- Внутри — одно или несколько **обращений к модели** (`ai_runs`) и **доменных
  действий** (созданные объекты, ошибки, отказы).
- Ключевые параметры: агент, владелец, организация, комната, скилл@версия, режим,
  capabilities, бюджет, версия ACL/политики, провайдер, модель, fingerprint ключа,
  температура, max tokens, набор инструментов, хэш промпта, ids входных объектов,
  токены, стоимость, задержка, статус, код ошибки, request id, время.

**Содержимое промпта и комнаты по умолчанию не пишется** — только хэш и ids. Если
понадобится разбор инцидента, включается отдельный режим с шифрованием и сроком
хранения, но это уже решение о персональных данных.

### 4.2. Цепочка хэшей

```sql
ai_runs(
  id uuid pk, org_id uuid, seq bigint, prev_hash text, hash text,
  agent_id uuid, task_id uuid, owner_id uuid, board_id text,
  skill text, skill_version int, capabilities text[], acl_version bigint,
  provider text, model text, credential_id uuid, key_fingerprint text,
  temperature numeric, max_tokens int, toolset text[],
  prompt_hash text, input_object_ids text[],
  prompt_tokens int, completion_tokens int, cost_usd numeric,
  latency_ms int, status text, error_code text, error_message text,
  request_id text, started_at timestamptz, finished_at timestamptz
)
```

- `hash = SHA-256(canonical_json(запись без hash, включая prev_hash))`.
- `seq` — на организацию, монотонный; `prev_hash` — хэш предыдущей записи.
- Запись делает только сервис; роли приложения запрещены UPDATE/DELETE.
- Раз в сутки последний `hash` выгружается в отдельное append-only хранилище
  (S3 Object Lock / внешний лог / нотариальный сервис). Без этого админ базы может
  переписать всю цепочку; с якорем — не сможет незаметно.
- API проверки: `GET /orgs/{id}/ai/audit/verify` пересчитывает цепочку и показывает
  первую расходящуюся запись. Читают `security_admin` и `org_admin`.
- Экспорт: JSON + подпись/хэш-манифест; срок хранения 365 дней, затем архив.

### 4.3. Что попадает в аудит, а что в журнал

- `audit_events` — управленческие действия: создан ключ, отозван, изменена политика,
  задача создана/отменена/завершена, отказ (`agent.denied`).
- `ai_runs` — техническая доказательная запись о каждом обращении к модели и его
  параметрах. Секретов и содержимого там нет.
- `agent_actions` — какие объекты созданы/изменены, с id и хэшем деталей.

## 5. Change sets и jobs (для карточек и не только)

Массовая операция не должна быть циклом «создай один объект» на стороне модели.

```json
{
  "boardId": "board_123",
  "operations": [
    { "op": "create_cards", "source": "selection", "textField": "text", "into": "column:todo" },
    { "op": "layout", "algorithm": "grid", "target": "created_cards" }
  ],
  "execution": { "mode": "async", "failurePolicy": "stop_after_failed_chunk" }
}
```

Обязательные свойства:

- временные ссылки (`ref`) до получения серверных id;
- валидация прав/типов/зависимостей/лимитов **до** исполнения;
- оценка объёма и стоимости (work units), отдельно от денег модели;
- preview и, для опасных операций, approval;
- идемпотентность по ключу;
- возобновление с контрольной точки;
- честная частичность: что выполнено, что отклонено, что ждёт;
- повторная проверка прав перед исполнением;
- аудит инициатора, агента и задачи.

Два режима: **ограниченная атомарная операция** (например, до 100 карточек — одна
Yjs-транзакция) и **большая возобновляемая работа** (чанки + прогресс). Не обещать
атомарность произвольно большому пакету.

## 6. Второй скилл: карточки

Требования вынесены в `spec/skills/cards.md`. Коротко: это доменная операция
«выделение → карточки», с режимами copy/move, целью standalone/kanban и бюджетом;
для больших объёмов — change set. MCP для неё не нужен.

## 7. MCP-фасад (когда появится)

Если внешние агенты (Claude, IDE, другие клиенты) должны подключаться к продукту,
MCP-сервер делается как отдельный процесс **над доменным API**:

- OAuth 2.1 resource server, токены с audience, без token passthrough (OWASP);
- scopes на организацию/комнату/задачу, не «доступ ко всему»;
- инструменты: `boards.list`, `boards.get`, `selection.read`,
  `change_sets.create/validate/execute/status/cancel`, `skills.list`, `skills.invoke`;
- инструменты возвращают сводки и handle, не тысячи объектов;
- никакого SQL, файловой системы и произвольного HTTP;
- rate limits и бюджеты на инструмент, а не только на HTTP;
- одинаковые проверки `agentEffective()` с HTTP-путём;
- журнал `ai_runs`/audit для каждого вызова инструмента.

MCP не заменяет скиллы и не является границей безопасности. Это адаптер.

**Реализовано в v0:** локальный stdio-сервер (`scripts/mcp-server.mjs`) с инструментами
`list_boards`, `list_skills`, `create_cards_change_set`,
`create_connector_change_set`, `set_connector_change_set`, `execute_change_set`,
`get_change_set`, `cancel_change_set`, `resume_change_set`. Токен агента, те же
`agentEffective()` и те же выключатели; чтения содержимого комнаты вне задачи нет.
Подробности — `spec/MCP.md`, ADR-068.

## 8. Порядок работ

| Этап | Состав | Готово, когда |
|---|---|---|
| **1. Ключи и журнал** | `ai_credentials`, envelope encryption, write-only API, выбор ключа, `ai_runs` + хэш-цепочка + verify | **сделано** (ADR-067); KMS — следующий шаг |
| **2. Карточки** | скилл `cards`, copy/move, standalone/kanban, чанки | **сделано**; 500 за задачу, прогресс, провенанс |
| **3. Change sets** | пакет операций, validate/estimate, preview, идемпотентность, cancel/resume | **сделано** для cards и связей (`create_connector`, `set_connector_*`); self-loop отклоняется |
| **4. MCP** | фасад с OAuth, tools, бюджетами | **v0 stdio** сделан; remote OAuth/SSE — следующий шаг |
| **5. SDK/jobs** | программный клиент, длительные jobs | отложено |

## 9. Решения, которые нужны до этапа 1

1. **KEK:** переменная окружения на VPS или облачный KMS? Для продакшена — KMS/HSM;
   env допустим только как временный.
2. **Политика ключей по умолчанию:** `either`, `org` или `personal`?
3. **Хранение якоря:** S3 Object Lock, внешний лог или отдельная БД?
4. **Содержимое промпта:** только хэш/ids (рекомендация) или опционально шифрованный
   снимок для разбора инцидентов?
5. **MCP:** нужен ли внешним клиентам в этом году, или сначала change sets?
6. **Карточки:** нужны ли поля assignee/due/tags; если да — это отдельное расширение
   модели и UI, а не только скилл.
