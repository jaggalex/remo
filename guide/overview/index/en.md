## In short

remo is a visual canvas where a team assembles plans, diagrams, kanban rooms and notes, then takes the result out as a file or hands it to an integration. A room is both the unit of work and the unit of access: whatever a person can do, they can do on a specific room and nowhere else.

The product is sized for a team of roughly ten people: an organisation (personal for every account, shared when needed), a few teams, and rooms that live for a long time and change often.

## What you get

| Result | How it is built |
|---|---|
| A team canvas | organisation → team → room; the role is granted on the room |
| Organisation home | room tiles with an emoji, search, sorting and trash |
| Visual material | sticky notes, shapes, text, frames, kanban, cards, connectors |
| Card work | status, assignee, date range, WIP, tags and links |
| Discussion | server threads on an object or point, pins, resolve, live reactions |
| Presentation | slide order, presenter and followers, late viewer |
| Protection from edits | author lock; the author or a room manager releases it |
| Real-time collaboration | cursors, presence, follow, "Bring everyone to me" |
| Controlled access | a role for a person or a team, a public link with a password and an expiry |
| Taking the result out | PNG or PDF by the chosen scope, a full JSON backup |
| Automation | agents, server commands, events, a signed webhook |
| Extension without foreign code | a declarative app panel |

## What to understand first

- **A room is the unit of access.** Permissions are not granted on an individual object: they are granted on a room and apply to everything on it.
- **A change counts as saved when the server confirms it,** not when you release the mouse. The save indicator says so plainly.
- **Extensions are first-party only.** No foreign code runs: an integration receives events and acts with a token, an app draws a panel from a schema.
