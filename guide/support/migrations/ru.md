## Как устроены миграции

Схема применяется самим сервисом при старте: `schema.sql` идемпотентен, версия хранится в `schema_meta`. Отдельной команды миграции нет — значит, **бэкап делается до обновления, а не после**. Текущая версия — 18.

Версия 17 добавила `org_id` в двенадцать таблиц, привязанных к комнате: существующие строки заполнены из комнат, новые получают организацию автоматически. Версия 18 добавила функции, которые от имени владельца ищут организацию, забирают задачи агента и события очереди, и довела построчную изоляцию организаций (RLS) до всех таблиц с данными организаций. Сами политики включаются командой `db:rls:enable`, а не применением схемы.

:::warning
Схема применяется при старте сервиса. Если сделать бэкап после обновления, откатываться будет некуда.
:::

## Две роли базы

С версии 18 сервис и обслуживание подключаются по-разному.

| Роль | Переменная | Что делает |
|---|---|---|
| Приложение, `remo_app` | `DATABASE_URL` | обслуживает запросы: только чтение и запись данных, без владения таблицами и без обхода политик |
| Владелец | `REMO_MIGRATION_DATABASE_URL` | применяет схему и запускает `db:check`, `db:orphans`, `db:rls:setup`, `db:rls:enable`; должен быть superuser или иметь `BYPASSRLS` |

Если `REMO_MIGRATION_DATABASE_URL` не задан, сервис использует `DATABASE_URL` для всего. В этом режиме изоляция организаций не работает, и включать политики на такой установке нельзя: приложение ходит от владельца.

Функции поиска организации и выдачи задач выполняются от владельца. Если владелец не superuser и не имеет `BYPASSRLS`, они не найдут строк: вход и задачи агента будут отвечать отказом.

## Порядок обновления

```sh
cd /srv/remo
systemctl stop remo-sync
sudo -u remo pnpm db:backup
sudo -u remo git pull
sudo -u remo pnpm install --frozen-lockfile
sudo -u remo pnpm build

# владелец: применить схему до включения политик
sudo -u remo env REMO_MIGRATION_DATABASE_URL=postgres://remo:…@127.0.0.1:5432/remo pnpm db:check

# комнаты без владельца: сначала список, потом решение
sudo -u remo env REMO_MIGRATION_DATABASE_URL=postgres://remo:…@127.0.0.1:5432/remo pnpm db:orphans --list
sudo -u remo env REMO_MIGRATION_DATABASE_URL=postgres://remo:…@127.0.0.1:5432/remo pnpm db:orphans --archive --yes

# роль приложения и политики
sudo -u remo env REMO_MIGRATION_DATABASE_URL=postgres://remo:…@127.0.0.1:5432/remo pnpm db:rls:setup
sudo -u remo env REMO_MIGRATION_DATABASE_URL=postgres://remo:…@127.0.0.1:5432/remo pnpm db:rls:enable
sudo -u remo env REMO_MIGRATION_DATABASE_URL=postgres://remo:…@127.0.0.1:5432/remo pnpm db:rls --check
sudo -u remo env REMO_MIGRATION_DATABASE_URL=postgres://remo:…@127.0.0.1:5432/remo pnpm db:rls:enable --check

systemctl start remo-sync
```

`db:check` применяет схему, но политики не включает: их включает `db:rls:enable`. `db:rls:setup` создаёт `remo_app`, если её нет, снимает `SUPERUSER` и `BYPASSRLS` и выдаёт права только на данные и функции, без владения таблицами. Чтобы роль могла войти по паролю, задайте `REMO_APP_DB_PASSWORD` в том же окружении.

1. Остановите сервис: он допишет комнаты в базу.
2. Сделайте бэкап и убедитесь, что файл появился в списке.
3. Обновите код и зависимости.
4. Соберите статику: несобранный фронтенд даст старую вкладку на новом API.
5. Примените схему от владельца: `pnpm db:check`.
6. Найдите комнаты без владельца и архивируйте их или назначьте владельца.
7. Создайте роль приложения и включите политики.
8. Запустите сервис.

## Комнаты без владельца

Комната без владельца закрыта: API и сокет отказывают, в списке комнат её нет. После обновления такие комнаты сами не откроются, а автоматического удаления нет: строка остаётся в базе, пока её не закрепят или не назначат ей владельца.

```sh
pnpm db:orphans --list
pnpm db:orphans --archive --yes
pnpm db:orphans --assign <roomId> --user <email>
```

- `--list` только показывает список, ничего не меняя.
- `--archive --yes` убирает все комнаты без владельца в архив, с записью в аудит.
- `--assign <roomId> --user <email>` назначает владельца, когда он известен: берётся личная организация человека, а если её нет — самая ранняя активная, и самая ранняя команда в ней; команда создаётся, если её нет.

:::warning
`--archive --yes` меняет все комнаты без владельца сразу. Данные не удаляются: комнату можно вернуть закреплением или назначением владельца.
:::

## Бумажная палитра

С 2026-11-07 заливки 100 и 300 стали бумажными. Комнаты, покрашенные раньше, остаются яркими, пока их не перекрасят. Команда переводит их на новые тона разом: у каждого прежнего цвета есть пара того же тона и уровня.

```sh
pnpm db:repaint
pnpm db:repaint --apply --yes
pnpm db:repaint --room <roomId> --apply --yes
```

- Без флагов команда только показывает комнаты и число объектов, ничего не меняя.
- `--apply --yes` перекрашивает стикеры, фигуры, линии и акценты колонок канбана. Каждая комната получает одно обычное изменение в истории и запись `board.palette.repainted` в аудите.
- Цвета из ещё более старой палитры на 22 цвета не трогаются: точной пары у них нет, в окне они остаются «Своим цветом».
- Повторный запуск ничего не находит. Комнату, восстановленную из старого бэкапа, можно перекрасить снова.

:::warning
Запускайте при остановленном сервисе и после бэкапа. Открытая комната держит документ в памяти и может затереть изменение команды.
:::

## Проверка после старта

```sh
curl -s http://127.0.0.1:1234/health
journalctl -u remo-sync -n 50 | grep -i 'schema\|error'
```

- `health` отвечает `ok`, версия схемы в логе совпадает с ожидаемой.
- `pnpm db:rls --check` не находит пробелов, `pnpm db:rls:enable --check` подтверждает применённый набор политик.
- `pnpm db:orphans --list` не находит комнат без владельца.
- Откройте комнату и сделайте правку: индикатор должен дойти до **сохранено**.
- Проверьте один вход и одну ссылку.
- Откройте обсуждение: старые треды на месте, новый комментарий сохраняется.
- Создайте комнату: она появляется в списке и открывается у владельца.

## Ломающие изменения

| Что | Как пережить |
|---|---|
| Переименование `remiro` → `remo` (2026-10-26) | переменные `REMO_*`, cookie `remo_session`, база `remo`; все сессии разлогиниваются |
| Смена имени cookie | миграции нет: cookie — это и есть механизм |
| Новый обязательный ключ (например, `REMO_KEK`) | задайте до старта, иначе функции ответят «locked» |
| Изоляция организаций (схема 18) | две роли: `remo_app` в `DATABASE_URL`, владелец в `REMO_MIGRATION_DATABASE_URL`; без `db:rls:setup` и `db:rls:enable` политики не работают |
| Бумажная палитра (2026-11-07) | необязательно: `pnpm db:repaint`, затем `--apply --yes` при остановленном сервисе; без этого старые комнаты остаются яркими |
| Комната без владельца закрыта (2026-11-06) | до старта трафика: `pnpm db:orphans --list`, затем `--archive --yes` или `--assign <room> --user <email>`; неперенесённые комнаты останутся закрытыми |

## Если что-то пошло не так

1. Не запускайте старую версию поверх новой схемы.
2. Остановите сервис и восстановите бэкап.
3. Если база обновлена, а код старый — верните код и восстановите базу вместе, а не по отдельности.
4. Если после включения политик запросы возвращают пусто, проверьте, что сервис подключён как `remo_app`, а владелец имеет `BYPASSRLS`. Команды, которая снимает политики, нет: откат — из бэкапа.
