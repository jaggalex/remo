## Что получится

Работающая установка на одном сервере: nginx терминирует HTTPS, sync-сервис держит комнаты и API, Postgres хранит комнаты и доступ.

**Один экземпляр.** Комнаты, открытые сокеты и проверка доступа живут в процессе; две копии за балансировщиком не увидят комнат друг друга. В этой версии масштабирование — вверх, не вширь.

## Подготовка

Ubuntu 24.04, Node 22 LTS, pnpm 11, Postgres 16. Нужны `nginx`, `certbot`, `git`, `ufw`.

```sh
apt install -y nginx certbot python3-certbot-nginx git curl ufw
corepack enable && corepack prepare pnpm@11.2.2 --activate
useradd --create-home --shell /bin/bash remo
install -d -o remo -g remo /srv/remo
```

## Шаги

1. Код: `sudo -u remo git clone <repo> /srv/remo && cd /srv/remo && sudo -u remo pnpm install --frozen-lockfile`.
2. База: `POSTGRES_PASSWORD='<сильный>' POSTGRES_PORT=127.0.0.1:5432 pnpm db:up`, затем примените схему от owner-роли: `REMO_MIGRATION_DATABASE_URL=postgres://<owner>:<пароль>@127.0.0.1:5432/remo pnpm db:check`. Порт с хостом обязателен: без него Postgres слушает все интерфейсы. `db:check` применяет схему, но не включает политики RLS.
3. Роли и RLS: owner-роль должна быть superuser или иметь `BYPASSRLS`. Создайте роль приложения и включите политики:
   ```sh
   export REMO_MIGRATION_DATABASE_URL=postgres://<owner>:<пароль>@127.0.0.1:5432/remo
   REMO_APP_DB_PASSWORD='<пароль приложения>' pnpm db:rls:setup
   pnpm db:rls:enable
   pnpm db:rls --check
   pnpm db:rls:enable --check
   ```
   `remo_app` получает только DML, без владения таблицами и без `BYPASSRLS`; сервис работает от неё. `db:rls --check` проверяет все таблицы с данными организаций, `db:rls:enable --check` — применённый набор.
4. Окружение: создайте `/srv/remo/.env` с `DATABASE_URL` (роль `remo_app`), `REMO_MIGRATION_DATABASE_URL` (owner), `NODE_ENV=production`, `PORT=1234`, `REMO_APP_ORIGIN`, `REMO_CORS_ORIGIN`, `REMO_METRICS_TOKEN`, `REMO_KEK`, `REMO_KEK_ID`; `chmod 600`.
5. Сборка: `sudo -u remo pnpm build`. Статика окажется в `apps/web/dist`.
6. Сервис: скопируйте `deploy/remo-sync.service` в `/etc/systemd/system/`, включите и запустите.
7. nginx: скопируйте `deploy/nginx-remo.conf`, замените домен, включите сайт, `nginx -t && systemctl reload nginx`, затем `certbot --nginx -d <домен>`.
8. Портал документации: `pnpm guide:build` и `rsync -a --delete docs-site/ /srv/remo/docs-site/`; nginx отдаёт его по `/guide/`.

## Почта

По умолчанию `REMO_MAIL_DRIVER=disabled`: сброс пароля и подтверждение адреса не показываются, письма не уходят. Это безопасное состояние — включайте почту, когда домен готов.

1. Отправляйте с отдельного поддомена, например `mail.example.com`, а не с основного: репутация писем не смешивается с приложением. Адрес в `REMO_MAIL_FROM` должен быть на этом поддомене.
2. Добавьте домен у провайдера (Resend или SMTP-сервис) и создайте записи DNS:
   - SPF — TXT на `mail.example.com`: `v=spf1 include:<провайдер> -all`;
   - DKIM — TXT; имя и значение выдаёт провайдер;
   - DMARC — TXT на `_dmarc.mail.example.com`: `v=DMARC1; p=none; rua=mailto:<ящик отчётов>`. Начните с `p=none`: политика только наблюдает и не отклоняет письма, пока вы проверяете отчёты.
3. Задайте `REMO_MAIL_DRIVER`, `REMO_MAIL_FROM` и ключ выбранного драйвера: `REMO_RESEND_API_KEY` для `resend` или `REMO_SMTP_URL` для `smtp`. SMTP принимает только порты 465 и 587. `REMO_APP_ORIGIN` должен быть `https` без завершающего `/`.
4. Перезапустите сервис. При неполной конфигурации он не стартует: это лучше, чем тихо терять ссылки сброса.
5. Проверьте доставку: `pnpm mail:test --to <ваш адрес>`. Письмо проходит через настоящую очередь; команда печатает id отправленного письма или причину отказа.
6. Разберите неудачи: `pnpm mail:dead` показывает последние 50 писем, которые не удалось отправить. `pnpm mail:dead --retry <id>` возвращает письмо в очередь, только если его ссылка ещё цела; после обычной ошибки ссылка стёрта, и человеку нужно запросить новое письмо.

`console` в production запрещён: он печатает ссылки в журнал сервиса.

## AI-шлюз

Шлюз выносит вызовы моделей на отдельный сервер: remo отправляет запрос по туннелю, а к провайдерам выходит только шлюз. Он необязателен. Без него агенты ходят к провайдеру напрямую, как раньше; в нашем сервисе шлюз включён, чтобы управлять списком провайдеров, выключателями и лимитами.

Нужны два сервера: с remo и отдельный, 1 vCPU и 1 ГБ памяти достаточно. На обоих — `wireguard-tools`, на сервере шлюза ещё `nftables`.

1. **Туннель.** Подсеть `10.77.0.0/30`: remo — `10.77.0.1`, шлюз — `10.77.0.2`. Ключи создайте на каждой машине, публичные обменяйте, в `AllowedIPs` оставьте только адрес другой стороны. Готовые конфигурации и порядок шагов — в `deploy/ai-gateway/wireguard.md`. Не направляйте в туннель весь трафик: иначе изоляция исчезнет.
2. **Межсетевой экран.** На сервере шлюза примените `deploy/ai-gateway/nftables.conf`: SSH только с ваших адресов, UDP WireGuard только с адреса remo, на `wg0` — только TCP 8080 от `10.77.0.1`. Исходящие — только TCP 443 и DNS. Порт 8081 для управления слушает `127.0.0.1` и наружу не открывается.
3. **Запуск.** Выберите один способ:
   - compose: `deploy/ai-gateway/compose.yml`, переменные в `/etc/remo-ai-gateway/gateway.env`, состояние в `/var/lib/remo-ai-gateway`;
   - systemd: `deploy/ai-gateway/remo-ai-gateway.service`.

   Оба запускают один процесс от отдельного пользователя, с неизменяемой файловой системой и записью только в каталог состояния. Не включайте оба сразу. Пользователя `remo-gateway` и каталоги создайте по списку в начале `compose.yml`.
4. **Реестр.** Возьмите за основу `config.example.json` из каталога шлюза и сохраните как `/etc/remo-ai-gateway/config.json` с правами 600; владелец — пользователь шлюза. Перечислите провайдеров, модели, регионы, таймауты и лимиты. Ключи установки положите в `gateway.env` под именами из `keyEnv`. Чего нет в реестре, того нет: произвольный адрес провайдера отклоняется.
5. **Сертификат.** Выпустите самоподписанный сертификат с IP-адресом `10.77.0.2` в SAN и положите его и ключ в `/etc/remo-ai-gateway/tls/` с владельцем-пользователем шлюза. На сервере remo задайте `REMO_AI_GATEWAY_URL=https://10.77.0.2:8080`, общий `REMO_AI_GATEWAY_TOKEN`, PEM сертификата в `REMO_AI_GATEWAY_CA` и регион в `REMO_AI_REGION`. Сертификат закрепляется в sync: без пина соединение не установится. PEM многострочный, поэтому в systemd `EnvironmentFile` его не задать: sync запускается через обёртку, которая читает файл сертификата и экспортирует переменную.
6. **Проверка.** С сервера remo: `curl --cacert gateway-ca.pem https://10.77.0.2:8080/healthz` → `{"status":"ok"}`. На сервере шлюза: `remo-gw status` и `remo-gw providers`. Затем запустите задачу агента в комнате.

`remo-gw` работает на сервере шлюза и вызывает управляющий API на `127.0.0.1`. Токен лежит в `/etc/remo-ai-gateway/admin.token`.

| Команда | Что делает |
|---|---|
| `remo-gw status` | версия, конфигурация, выключатели, нагрузка |
| `remo-gw providers` | провайдеры, модели, регионы, ошибки и задержка |
| `remo-gw limits` | действующие лимиты и переопределения |
| `remo-gw usage` | токены и стоимость по дням и организациям |
| `remo-gw kill provider openrouter` | выключить провайдера без перезапуска remo |
| `remo-gw unkill provider openrouter` | вернуть провайдера |
| `remo-gw reload` | перечитать `config.json` |

### Наблюдение и тревоги

- `/healthz` отвечает без токена и без подробностей; `/metrics` — только с `GATEWAY_METRICS_TOKEN`.
- Тревога, если доля ошибок провайдера выше 20% за 10 минут.
- Тревога, если агенты получают `503 AI_GATEWAY_UNAVAILABLE`: задачи отвечают «ИИ временно недоступен», а комната продолжает работать. Смотрите журнал sync и `remo-gw status` на шлюзе.
- Тревога по суточной стоимости: `remo-gw usage` и `limits.global.costPerDay`.

Шлюз не меняет юридическую сторону: если текст уходит к зарубежному провайдеру, это по-прежнему передача данных за границу. Список провайдеров в реестре и политика конфиденциальности должны совпадать.

### Адрес для внешних агентов

Внешним агентам и интеграциям отдайте отдельное имя `agents.<домен>`: `deploy/nginx-remo-agents.conf` проксирует только API агентов и интеграций, без статики и сокетов, со своими лимитами по адресу и по токену. На основном домене bearer-токены продолжают работать для совместимости, но в инструкциях указывайте `https://agents.<домен>`.

### Чего может не быть у self-host

Если `REMO_AI_GATEWAY_URL` не задан, агенты вызывают провайдера напрямую: ни туннеля, ни второго сервера, ни `remo-gw`. Такая установка работает как раньше. Включайте шлюз, когда нужны общий список провайдеров, выключатели и лимиты по организациям.

## Проверка

```sh
curl -s https://<домен>/api/health          # {"ok":true,"version":"0.2.0","build":"1247",…}
curl -sI https://<домен>/                    # 200
curl -sI https://<домен>/guide/              # 200, документация
```

В браузере: регистрация, комната, вторая вкладка в приватном окне, перетаскивание стикера. В сети сокет должен показать `101 Switching Protocols`.

Если почта включена, отправьте себе письмо командой `pnpm mail:test --to <ваш адрес>` и откройте ссылку из него. Список писем, которые не удалось отправить, показывает `pnpm mail:dead`.

## Ограничения

- Один процесс: перезапуск рвёт сокеты, клиенты переподключаются сами.
- Одна задача агента выполняется за раз: медленная модель задерживает очередь агентов, но не холст.
